# Modernization Roadmap — 2026

Goal: bring the stack up to current standards while keeping the clean-architecture
structure (UI / Domain / Data + DI container) as the template's core teaching value.
Staying a Vite SPA — no metaframework migration in scope.

The main-chunk size barely moved because the app's weight is almost entirely vendor code shared across every route (MUI + `@mui/x-data-grid` account for the large majority of module count in the stats treemap, per `@inversifyjs/core`/`axios`/`react-i18next` next), not per-route logic — `ProductsTable` (MUI DataGrid) is used on both Home and Favorites, so it can't be route-split anyway. Net effect: the code-splitting bug is fixed (routes now genuinely lazy-load on navigation instead of all shipping in the entry chunk), but bundle-size impact is minor given this app's size/route count; the real lever for size would be trimming/replacing `@mui/x-data-grid`, which is a separate, larger decision. `tsc`, lint (0 errors, same 6 pre-existing `no-explicit-any` warnings), build, and all 7 tests pass.
- [x] Architecture revisit: re-evaluated RTK Query vs. the hand-rolled axios repositories, and react-router v7's data APIs — decided to keep both as-is. **RTK Query**: today's `@reduxjs/toolkit` usage (`FavoriteSlice`, `CountrySlice`, `SearchSlice`) is pure client state, not server-state caching, so adopting RTK Query would be a net-new layer, not a swap for existing code. More importantly, it would collapse the Data layer's repository/DTO abstraction (`ProductRepositoryImpl`, `SearchRepositoryImpl`, etc. — the interfaces the Domain layer depends on via Inversify DI) into Redux-coupled hooks generated from API slices, which breaks the Clean Architecture boundary this template exists to demonstrate. Not worth it for an app this size with no cache-invalidation pain today. **react-router v7 data APIs**: loaders/actions run at the router layer and would mean route definitions reaching directly into data-fetching, again bypassing the repository/use-case layers instead of composing with them. The current pattern (components call use-cases via hooks, use-cases call repositories) keeps that boundary intact and there's no concrete pain point (slow waterfalls, prop-drilling) motivating the change. Revisit only if a real requirement forces it (e.g. server-driven route data, streaming SSR) — not preemptively.

**Explicitly out of scope for Phase 5** (picked up in Phase 6): TypeScript 5.9 → 7.0.2 is the native Go-based compiler rewrite, not a routine bump — the wider ecosystem (ESLint's typescript-eslint, ts-node-style tooling) needs to catch up first. RTK Query and further react-router v7 data-API adoption remain deliberate architectural decisions, tracked as Phase 6's architecture revisit item.

## Phase 8 — 2026 template stack: compiler, tooling, bundle weight

Goal shift from Phase 8 on: routine dependency currency is done (engines, ESLint, TS, Vite, MUI, React, react-router are all on latest majors as of Phase 7). This phase is about adopting what's actually considered current/recommended practice for a React template in 2026, not just bumping numbers.

- [x] Adopt **React Compiler** (`babel-plugin-react-compiler`) for React 19. Confirmed stable status first: `babel-plugin-react-compiler@1.0.0` is tagged `latest` on npm (the `rc`/`beta`/`experimental` dist-tags are separate, older tracks) — out of RC, safe to adopt. The companion ESLint package (`eslint-plugin-react-compiler`) is still stuck on a `19.1.0-rc.2` release from over a year ago and caps at that; the current recommended path (per React's own docs) is instead `eslint-plugin-react-hooks@7.1.1`, which folded the compiler's Rules-of-React lint rules into its `recommended-latest` flat config as of v5+ and declares `peerDependencies: { eslint: "... || ^10.0.0" }` — no separate compiler ESLint package needed. Wired the babel plugin into `vite.config.ts`'s existing `@vitejs/plugin-react()` call via `babel: { plugins: [["babel-plugin-react-compiler", {}]] }`, and added `reactHooks.configs.flat["recommended-latest"]` to `eslint.config.js`'s `extends` array (flat config needs the `.flat` namespace specifically — `reactHooks.configs["recommended-latest"]` on its own is the legacy eslintrc shape and throws at ESLint 10 startup). Turning the new lint rules on immediately caught two real, pre-existing Rules-of-React violations in `Search.tsx` that happened to work today by accident but would silently break under compiler auto-memoization: (1) reading a `useRef(...).current` value during render instead of only inside the documented lazy-init `if (ref.current === null)` idiom, and (2) synchronously calling `setState` inside a `useEffect` to mirror a changed `string` prop into local state, which causes an extra cascading render. Fixed both — the ref now stays behind `debouncedSearchRef.current` accessed only in the event handler/effect cleanup (never assigned to a render-scope variable), and the prop-mirroring effect was replaced with the React-documented "adjust state during render" comparison (`if (string !== prevString) { setPrevString(string); setSearchStr(string) }`), which also removes a render than the effect version cost. `tsc --noEmit`, lint (0 errors, same pre-existing `no-explicit-any`/`exhaustive-deps` warnings), build, and all 7 tests pass. Confirmed the compiler actually ran by grepping the production bundle for injected `useMemoCache` calls (present) — no `react-compiler-runtime` package was pulled in, since React 19 ships the compiler's runtime helper built in. Bundle size is a wash as expected (compiler output is optimized JS, not an added runtime dependency): main chunk `index.js` 1,189.16 kB (361.03 kB gzip) vs. the Phase 6 baseline of 1,191 kB (361.53 kB gzip) — within normal build-to-build noise.
